# 修正依頼: BW・XY世代のカードデータ取得

`cardData.json` に未収録の BW・XY 世代（2011〜2016）を追加する。

**このタスクは調査フェーズを含む。ステップ1の結果が出るまで、データ取得の実装に着手しないこと。**
番号体系が確認できないまま取り込むと、誤ったカード番号で出品する事故につながる。

---

## 背景

現在の `cardData.json` に収録されているシリーズは以下の10種のみ:

```
SV=5,346  S=4,659  PCG=722  e=492  PMCG=457  M=417  neo=323  VS=143  SM=48  web=47
```

`DP / DPt / L / BW / XY / XYb / ADV` はゼロ。`SERIE_ORDER`（`src/App.jsx`）にはキーだけ定義されている。

過去の調査（CLAUDE.md「収録範囲の限界」セクション）で見送りとした理由:

- **TCGdex**: `ADV/L/XY/XYb/SM` はセットの入れ物だけでカード個票がほぼ空（例外: CP1のみ34枚）。
  `DP/DPt/BW` はシリーズ自体が存在しない
- **公式サイト**: `resultAPI.php` は `cardID / cardThumbFile / cardNameViewText` の4項目のみで
  カード番号を含まない。`details.php` も DP1 世代はカード番号を表示するUI要素自体が無い

**この調査は DP1 に対して行われたものである。BW・XY 世代で同じとは限らない。**
CLAUDE.md にも「新しいテンプレートにのみある機能」と記録されており、
BW・XY は DP より5〜9年新しいため、テンプレートが変わっている可能性がある。

### 今回新たに判明した手がかり

公式サイトの商品ページに、**拡張パック単位のカードリストURL**が存在する。

```
XY1 コレクションX: https://www.pokemon-card.com/card-search/index.php?mode=statuslist&pg=404
XY1 コレクションY: https://www.pokemon-card.com/card-search/index.php?mode=statuslist&pg=405
```

`pg` は商品ごとに割り振られた番号。既存の `scrape-official-images.mjs` は
`resultAPI.php?regulation_sidebar_form=all&page=N&sortBy=new` という**全カード横断**の
取得しかしていないが、`pg` を使えば**セット単位**で引ける可能性がある。

セット所属が分からないことが従来のネックだったので、ここが突破口になりうる。

---

## ステップ0: リポジトリを private に戻す（着手前に必須）

現在 `yoichi-project01/ptcg-ebay-tool` は public。外部サイトから取得したカードデータを
public リポジトリにコミットすると、それ自体が再配布にあたる。

レビュー目的の公開は終わっているので、**GitHub の Settings から private に変更してから**
このタスクに着手すること。

なお公式サイトには「このホームページに掲載された画像その他の内容の無断転載はお断りします」
と明記されている。カード名・番号といった事実データと、画像・テキストの転載は
性質が異なるが、いずれにせよ private 前提で進める。

---

## ステップ1: 番号取得経路の検証（調査タスク・XY1のみ）

**対象を XY1（コレクションX、`pg=404`）1セットに絞って**、以下の3経路を順に試す。
1つでも成功したら残りは省略してよい。結果は必ず CLAUDE.md に記録すること。

### 経路A: `details.php` にカード番号が表示されるか

既存の `fetchCardLocalNumber()`（`scrape-official-images.mjs` の115行目付近）は
`${API_BASE}/card-search/details.php/card/${cardId}` を取得している。

1. `pg=404` の `resultAPI.php` 相当のエンドポイントから XY1 の `cardID` を数件取得する
2. その `cardID` で `details.php` を取得し、HTML内にカード番号（`001/060` 等）を示す
   要素があるか確認する
3. あれば、既存の `fetchCardLocalNumber()` のセレクタが流用できるか確認する

**これが成功すれば最良。** 公式が一次情報源であり、番号が検証済みの状態で取得できる。

### 経路B: 掲載順が番号順であるという仮説の検証

経路Aが失敗した場合。`pg=404` のリストが**カード番号順に返ってくる**なら、
配列のインデックス＋1が番号になる。

検証方法:

1. XY1 のカード画像を10〜20枚ダウンロードする（`cardThumbFile` から取得できる）
2. 画像に印刷されている番号を**目視で読み取る**
3. リスト内での位置と一致するか照合する

**必ず先頭・中間・末尾から満遍なくサンプリングすること。** 先頭だけ一致していても、
途中でプロモやシークレットが挿入されて順序が崩れる可能性がある。

**1枚でも不一致があれば、この経路は不採用とする。** 部分的に正しいデータは、
全部間違っているデータより危険（どこが正しいか分からないため）。

### 経路C: TCGdex の再確認

過去の調査から時間が経っている。`https://api.tcgdex.net/v2/ja/sets/xy1` 等を叩き、
`cards` 配列が埋まっていないか確認する。埋まっていれば最も低コスト。

XY 系のセットIDは TCGdex のシリーズ一覧（`/v2/ja/series/xy`）から取得すること。

### ステップ1の受け入れ条件

- 3経路それぞれの結果（成功/失敗と、その根拠）を CLAUDE.md に記録している
- 成功した経路がある場合、XY1 の全カードについて「番号・日本語名」の対応表が
  取得でき、うち10枚以上を画像と目視照合して一致を確認している
- **どの経路も失敗した場合はここで停止し、報告すること。** 推測でデータを入れないこと

## ステップ2: データモデルの確認

ステップ1で番号形式が判明したら、既存のデータモデルに乗るか確認する。

BW・XY 世代は `001/060` のようなセット内番号だと想定しているが、**確認が必要**。
ポケモンWikiの記述では「コレクションナンバー」という語が使われており、
セット内で連番であることは読み取れるが、`番号/総数` 形式かどうかは未確認。

### 確認事項

1. **番号形式**: `001/060` 形式か、番号のみか
2. **総数（`of`）**: セット総数が取得できるか。できない場合はカード数から算出してよいか
   （シークレットカードがあると総数＜最大番号になる点に注意）
3. **エキスパンションマーク**: XY世代には拡張パックとは別のエキスパンションマークが
   存在する。例えば XY5「ライジングフィスト」収録のサナとティエルノは
   右下のマークが `XYA` になっている。同一パック内でマークが混在するため、
   `setCode` をどう持つか判断が必要
   - 案: `setCode` はマーク準拠（`XYA`）、収録商品は別フィールドで持つ
   - どちらにするかはステップ1で実物の分布を見てから決める
4. **レアリティ表記**: 既存の `RARITIES` 配列でカバーできるか。
   XY世代は `RR` `UR` `SR` に加えて `BREAK` などがある。不足があれば追加する

### 受け入れ条件

- 上記4点の結論を CLAUDE.md に記録している
- 既存の `cardNoOf` / `buildSku` / `buildItemSpecifics` / `buildSingleTitle` が
  そのまま使えるか、分岐が必要かを判断している
- 分岐が必要な場合、旧裏（`buildVintageTitle`）と同じパターンで実装する方針とする

## ステップ3: XY1 の取り込み（1セットのみ）

ステップ2の結論に沿って、XY1 だけを `cardData.json` に追加する。

- `scripts/scrape-bw-xy.mjs` を新規作成する
- 既存スクリプトの規約に従うこと:
  - `filename-utils.mjs` の `isUsableImage` / `writeFileAtomic` / `MIN_IMAGE_BYTES` を使う
  - `CONCURRENCY = 3`、`DELAY_MS = 400` 程度（`scrape-pcg-search.mjs` に合わせる）
  - すべての `fetch` に `AbortSignal.timeout` を付ける
  - 失敗ページを集計し、一定数を超えたら異常終了する（`MAX_FAILED_PAGES` パターン）
- **英語名は取得しない。空欄のままにする。**
  日本語版セットの英語名は信頼できるソースが無いことが確認済み。
  UI の「英語名なし」警告に任せる

### 受け入れ条件

- `node scripts/check-row-alignment.mjs` が exit 0 で通る
- `python3 scripts/detect-contaminated-en-names.py` が0件（英語名を入れていないので当然だが確認する）
- XY1 のカードを10枚無作為抽出し、画像と `cardData.json` の番号・名前が一致することを
  目視で確認する
- `npx vitest run` が全件通る
- 既存セットのデータが1件も変更されていない（`git diff` で確認）

## ステップ4: 横展開

XY1 が問題なく取り込めたら、残りに広げる。

### 対象セットの列挙方法

セットコードを推測で書かないこと。以下から実際に列挙する:

- 公式商品情報ページ `https://www.pokemon-card.com/products/` の BW / XY カテゴリ
- 各商品ページに記載されている `pg=` の値を収集する

拡張パック本弾のほか、構築済みデッキ・プロモ（`BW-P` / `XY-P`）・
コンセプトパック（`CP1`〜）が存在する。**まず拡張パック本弾のみを対象とし、
それ以外は本弾が完了してから判断する。**

### 進め方

1セットずつ取り込み、都度ステップ3の受け入れ条件を確認する。
まとめて全部取り込んでから検証すると、問題があったときの切り分けができない。

XY世代 → BW世代の順に進める。XY のほうが新しくテンプレートが安定している可能性が高く、
またメガ進化EX・BREAK など eBay で動く弾が集中しているため、価値が先に出る。

## 対象外（今回やらないこと）

- **DP / DPt 世代**: コレクション番号が `DPBP#001〜530` という種族単位の通し番号で、
  1つの番号に「拡張パック版」「構築済みデッキ版」「1st Editionマークの有無」で
  最大4種類のカードが存在する。既存のデータモデルでは一意に特定できない。
  対応する場合は `printVariant`（旧裏で実装済みの仕組み）を拡張する設計になるが、
  BW・XY が完了してから別タスクとする
- **L（LEGEND）世代**: 番号体系が未調査
- **ADV 世代**: `pcg-search.com` に含まれており別経路で取得可能。別タスクとする
- **英語名の取得**: 信頼できるソースが無い。空欄のままとする

---

## やってはいけないこと

1. **番号が検証できないまま取り込まないこと。** ステップ1で全経路が失敗したら停止して報告する
2. **掲載順＝番号順の仮説を、検証せずに採用しないこと。** 必ず画像と目視照合する
3. **英語名を推測で埋めないこと**（過去に revert 済み。CLAUDE.md 参照）
4. **`robots.txt` で自動アクセスを拒否しているサイトから取得しないこと。**
   `pokeca.itemlist.info` は内容が充実しているが robots.txt で拒否している。参照は手動のみ
5. **既存の10シリーズのデータを変更しないこと。** 追加のみ行う
6. **public リポジトリの状態で取得データをコミットしないこと**（ステップ0）

---

## 補足: 想定される所要

ステップ1の調査が最も重要で、ここで方向性が決まる。経路Aが通れば以降は既存スクリプトの
流用でほぼ済むが、経路Bになると1セットごとに目視検証が必要になり、コストが跳ね上がる。
経路Cが通れば最短。

**ステップ1の結果を見てから、ステップ4に進むか判断する。** 目視検証が必要な場合、
実際に扱うセットだけに絞る（手動登録に近い運用にする）ほうが合理的な可能性がある。
